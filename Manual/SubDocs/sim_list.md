# Simulation list
The simulation list provides a list of simulations to be performed. Note that the parent folder for the project is specified using the ```project folder``` key in the *sims_config.json* file. The fields contained in the list are as follows:

**Table 1: Fields used in the simulation list (Excel spreadsheet).** 

| Field | Description |
| ----------- | ----------- |
| ```Include```|If ```no```, this simulation is skipped. Else, ```yes``` to include this simulation. |
| ```Method```| One of ```monte carlo```, ```ensemble``` or ```reservoir routing```. The first two run the hydrologic model; ```reservoir routing``` re-routes the inflow hydrographs a previous run stored, under a different dam rating curve, without re-running the hydrology - see [the reservoir routing method](#thereservoirroutingmethod) at the end of this page. |
| ```Duration```| The storm duration in hours if running a monte carlo simulation. Not used for ensemble simulations - specified in the [ensemble config file](config/EnsembleConfig.md). Not used for reservoir routing, where the durations come from the stored results being re-routed.  |
| ```Run models```| If ```yes```, the RORB/URBS models are run for this simulation. Else, ```no``` if not wanting to run the models - only analysing existing results. For the Monte Carlo method, ```storms only``` runs the storm generation and sampling but skips the hydrologic model - useful for cheap runs of [the sub-burst check](sub_burst_check.md) and for calibrating temporal pattern weights. For reservoir routing there is no hydrologic model to run: ```yes``` does the routing, and ```no``` re-analyses results that have already been routed. |
| ```Analyse results```| If ```yes```, the results from the simulation are analysed: applying total probability theorem for monte carlo and creating box plots and tables for ensemble events. Else, ```no``` if not wanting to analyse the results. A reservoir routing simulation is analysed the same way the results it was given were produced - by total probability theorem for Monte Carlo input, and by box plots, medians and critical durations for ensemble input. |
| ```Analyse sub-bursts```| ++Optional (monte carlo only):++ If ```yes```, a frequency curve of the sub-burst depths within the sampled storms is derived by TPT for each standard sub-duration and compared with the IFD (the ensemble AEP-neutrality check on embedded bursts). See [the sub-burst check](sub_burst_check.md). Outputs a quantile csv and plot per sub-duration, plus a neutrality summary csv of the TPT/IFD depth ratio at the standard AEPs; ratios above 1.0 indicate sub-bursts occur more often than the IFD implies. The sub-burst depths are recorded during the model runs (```subburst_<duration>h``` and ```ifd_<duration>h``` columns in the mcdf file), so the models must have been run with a version of Bryan that tracks them. |
| ```Store hydrographs```| Type ```yes``` if wanting to store all the modelled hydrographs for this simulation in a single csv file. Useful if wanting to use some results as boundary conditions for a hydraulic model or to check the results. Though, storing the results for thousands of runs takes a bit more time. |
| ```Mop up files```| The monte carlo simulations produce thousands of storm files and results files from the URBS model. Type ```yes``` here to delete these files - keeping file management tidier. A few storm files are skipped in the deletion to aid checking. Note that the peak inflow, lake level and outflow for each run are stored and output separately; so, are not deleted. |
| ```ADV```| The antecedent dam volume (ADV) for simulations. Four options are available: **1)** A fixed ADV can be set using a number (in ML). **2)** The full supply volume can be used by using the keyword ```fsv```. **3)** The keyword ```mav``` uses the volume the [lake config](config/LakeConfig.md) exceedance curve gives at ```z = 0``` - the median of the distribution that ```varying``` samples from - so the lake config file is also needed. Any ```volume_cap``` in that config applies, against the full supply volume of the dam being run. **4)** For the Monte Carlo method, a varying ADV can be used by using the keyword ```varying``` and supplying the lake config file (see below). <br><br>A reservoir routing simulation with **ensemble input** takes its ADV from this key, because an ensemble holds one starting volume for the whole run. On top of the four options above it also accepts ```database```, which reuses the ```ADV``` column of the input database - i.e. whatever the source run started from - for reproducing that run. ```varying``` is rejected. Note that ```fsv``` and ```mav``` resolve against the rating curve **being routed**, not the one the input database came from: this is what you want when re-routing under a different dam, as ```database``` would silently start every event at the old dam's full supply volume. A reservoir routing simulation with **Monte Carlo input** ignores this key and uses ```ADV source``` below instead. |
|```Baseflow```|++Optional++: This key can be used to switch baseflow on and off - it overrides the ```apply``` switch in the *urbs_config* file. |
| ```ADV source```| ++Optional (reservoir routing with Monte Carlo input only):++ Where the antecedent dam volume for each realisation comes from. Ignored, with a note printed, when the input is an ensemble - that takes a single ADV from the ```ADV``` key above. **1)** ```mcdf``` (the default, and what happens if this column is absent or blank) takes the ```ADV``` column of the input mcdf file. **2)** ```lake_z``` recomputes the ADV from the ```lake_z``` column of the input mcdf using the distribution in the [lake config file](config/LakeConfig.md) - so the ```Lake config``` key is also needed. This is how the one set of inflow hydrographs is re-routed under a different antecedent storage distribution without re-running the hydrology. **3)** ```lake_z correlated``` does the same, but first (re)applies the correlation layers in the lake config to ```lake_z``` against the mcdf ```rain_z```. Only use this where the mcdf was sampled *without* a correlation, as the ```lake_z``` written by a correlated Monte Carlo run already has the correlation in it. The resampled ADV is written to the ```ADV``` column of the output mcdf, with the original kept in an ```ADV_input``` column. Capping (the ```volume_cap``` key of the lake config) uses the full supply volume of the new rating curve. |
| ```Lake config```| Relative filepath to the [lake config file](config/LakeConfig.md), where the distribution and correlation for the ADV are set. Needed if the *varying* or *mav* keyword is used in the ```ADV``` key (see above), or if the ```ADV source``` key resamples the ADV for a reservoir routing simulation. |
|```Focal subcatchments``` | Filepath to a csv file containing a list of subcatchment areas upstream of the focal point for the hydrology. The area-weighted catchment average rainfall is computed from this (used for preburst depth computation and embedded burst filtering). The total catchment area (used for the ARF and selecting areal temporal patterns) is computed from the sum of these areas. |
| ```Config file```| Relative path to the main ensemble or monte carlo config file. For a reservoir routing simulation with Monte Carlo input, point this at the monte carlo config file that the input mcdf was generated with: the TPT parameters are read from its ```scheme_config``` (and, failing that, from the top level of the file), and the sampled rainfall in the mcdf is checked against them before the results are analysed. The **AEP of the PMP** does not need to be in this file: it is taken from the [IFD files config](config/IFDFilesConfig.md) that the [storm config](config/StormConfig.md) points at, which is where a Monte Carlo run gets it, so the routed quantile table has the same standard AEPs as the run it came from. An ```aep_of_pmp``` key here still overrides it. Not used by a reservoir routing simulation with ensemble input, which needs no scheme parameters - leave it blank. |
| ```TP weights```| ++Optional (monte carlo only):++ Relative path to a temporal pattern weights file (as written by ```util/CalibrateTpWeights.py```) to apply probability-weighted sampling of the temporal patterns - see [the sub-burst check](sub_burst_check.md). Rows are the weight groups (storm method, plus the frequency bin for ARR point patterns, e.g. *ARR point\|rare*); columns are the pattern indices 0-9. The weights compose with the D50 climate shift weightings. Cannot be combined with the ```tp``` replicate. Leave blank for the standard equal-probability sampling. |
| ```Replicates```| Used to replicate the monte carlo sampling in a previous simulation. Provide a list of components to replicate from a previous simulation; e.g. ```rz,tp,ilp,clp```. See Table 2 below for the key definitions. |
|```Replication file```| The relative path to the file used to replicate the sample scheme for the monte carlo simulations. |
| ```Exclusions```| Used for sensitivity testing of excluding some aspects of the simulations; e.g. ```ebf.d50```. See Table 3 below for the key definitions. |
|```Log file``` | Relative path to the log file created for this simulation. **One file per simulation**: where two or more included rows give the same path, the repeats are renamed by folding in the ```Output file``` name, and the renames are printed at the start of the batch. Without this they would overwrite each other and only one run's log would survive. For the *reservoir routing* method this column is optional - leave it blank and the log is written to the results folder as ```<Output file><Output suffix>_log.txt```. That log opens with a **SIMULATION INPUTS** block recording the whole sims list row, plus the absolute path, size and modification time of every input file, for QA. |
|```Output file``` | Relative path for output files for this simulation. |
| ```Input MCDF```| ++Reservoir routing only:++ Relative path to the results database of the run being re-routed - the *mcdf* of a Monte Carlo run or the results file of an ensemble run. May be ```.csv``` or ```.parquet``` (parquet needs ```pyarrow```). ```Input database``` is accepted as an alias, which reads better for ensemble input. Which scheme produced the file is worked out from its columns, so there is no key to keep in step with the data. |
| ```Inflow```| ++Reservoir routing only:++ Relative path to the stored inflow hydrographs of that run - one column per simulation, indexed by time in hours. May be ```.csv``` or ```.parquet```. These must have been kept, so the source run needs ```Store hydrographs``` set to ```yes```. An ensemble hydrograph file spans every duration at once and is padded after each duration's simulation period; that is handled. |
| ```ELS file```| ++Reservoir routing only:++ Relative path to the URBS ```.els``` elevation/storage file for the dam being routed. |
| ```SQ file```| ++Reservoir routing only:++ Relative path to the URBS ```.sq``` storage/discharge file for the dam being routed. Together with the ```.els``` and ```FSL``` this is the rating curve the flows are re-routed through - the whole point of the method is that it differs from the one the input database was produced with. |
| ```FSL```| ++Reservoir routing only:++ Full supply level in m AHD for the rating curve being routed. The full supply volume is read off the ```.els``` at this level, and the storages in the ```.sq``` (which are relative to full supply) are referenced to it. |
| ```Output suffix```| ++Optional (reservoir routing only):++ Appended to the output filenames, so the same source results can be re-routed under several rating curves without the outputs colliding. |
| ```Hydrographs folder```| ++Reservoir routing only:++ Folder for the routed level, outflow and volume hydrographs, written when ```Store hydrographs``` is ```yes```. Created if it does not exist. |
| ```Results folder```| ++Reservoir routing only:++ Folder for the routed results database, the quantile tables and the plots. Created if it does not exist. |
|```GWL```| ++Optional (used in Sunwater spec):++ The global warming level (in °C) relative to the hydrologic baseline period to apply to the simulation. Typically using 1.3°C for the near term, 1.8°C for the medium term, and 2.7°C for the long term. Note that if the ```GWL``` key is not used, the ```SSP``` and ```Year``` keys must be provided.|
| ```SSP```| ++Optional (not used in Sunwater spec):++ Shared Socioeconomic Pathway (SSP) to use for the global warming projection (climate change). Can be one of : SSP1-1.9, SSP1-2.6, SSP2-4.5, SSP3-7.0, SSP5-8.5. |
| ```Year```| ++Optional (not used in Sunwater spec):++ Climate horizon for the simulation. If the horizon falls within the base period (usually 1961 to 1990), no climate change adjustments are made. If the horizon falls before the warming projection period begins (2015), historical temperature anomalies are used and the SSP doesn't influence the temperature rise. |


**Table 2: Keys used for the replication of monte carlo sampling.**

| Key | Description |
| ----------- | ----------- |
|```rz``` | The rainfall sampling - standard normal variate |
|```tp``` | The temporal pattern sampling - integer from 0 to 9 |
|```stm```| The storm method sampling: ARR point, ARR areal, GSDM, and GTSMR. Use this one with care, as these are influenced by catchment size and storm duration. |
|```ilp```| The initial loss percentile (0-1) used for the scaling of the storm's initial loss.|
|```clp```| The continuing loss percentile (0-1) used for the scaling of the storm's continuing loss.|
|```pbp```| The sampling of the preburst percentile( 10% to 90%), which is then used to get the preburst proportion of the catchment average rainfall. |
|```lz```| The sampling of the antecedent lake volume - standard normal variate.|

**Table 3: Keys used for excluding some components of the modelling.**

| Key | Description |
| ----------- | ----------- |
|```pb``` | Exclude the residual preburst rainfall depth (after subtracting losses) from the storms. |
|```ebf``` | Exclude the filtering of embedded bursts |
|```d50```| Exclude the front loading shift in the temporal patterns due to climate change (probability weighted sampling). This shift is not applied in the ensemble simulations. |
|```ru```| Exclude the rainfall uplift due to climate change.|
|```lu```| Exclude the rainfall loss uplift due to climate change. |
|```clp``` | Exclude the sampling of continuing loss - a fixed CL is used. |

# The reservoir routing method
Setting ```Method``` to ```reservoir routing``` re-routes the inflow hydrographs stored by an earlier run through a different dam rating curve. The hydrology is not run again - the inflows are taken as given - so a set of alternative spillway or full supply level options can be assessed in seconds rather than by repeating the whole Monte Carlo or ensemble run. The source run must therefore have been done with ```Store hydrographs``` set to ```yes```.

The routing is the Modified Puls method in its storage-indication form, solved for every simulation at each timestep at once.

**It takes the output of either scheme.** Which one it has been given is worked out from the columns of the ```Input MCDF``` file - a Monte Carlo database carries the sample position of each realisation, an ensemble database carries each event's duration and temporal pattern - and that decides three things:

| | Monte Carlo input | Ensemble input |
| ----------- | ----------- | ----------- |
| antecedent dam volume | per realisation, via ```ADV source``` | one value for the run, via ```ADV``` |
| analysis | total probability theorem, giving quantile tables and frequency curves | box plots, the median pattern of each duration, and the critical duration per AEP |
| results database | ```<Output file>__mcdf.csv``` | ```<Output file><Output suffix>.csv```, with ```plots``` and ```csv``` sub-folders beside it |

> **Setting the starting volume when the dam changes.** For ensemble input, use an ```ADV``` of ```fsv``` or ```mav``` rather than ```database``` whenever the rating curve being routed is not the one the results came from. Both resolve against the new curve; ```database``` would start every event at the *old* dam's full supply volume, and nothing would look wrong in the output.

Every reservoir routing simulation writes a log file recording its inputs - see the ```Log file``` key in Table 1.
